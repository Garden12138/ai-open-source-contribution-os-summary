任务 `82c0ec73-3be6-4499-b806-45cd31430722` 已有真实实现、测试、独立审查和

**应当采用的交互方式**

借鉴 Codex 的重点是用户通过同一段对话持续交代工作、追加信息和查看结果。
官方资料区分运行中的排队追加与即时调整方向，说明两者具有不同语义。
本产品建议先可靠支持排队追加，再支持在安全边界调整；这是本项目的设计选择，
不意味着要复制 Codex 的全部功能或设置。[OpenAI 官方说明](https://developers.openai.com/blog/mastering-codex-remote-for-engineering)

输入区域只承担三种日常行为：

| 时机 | 用户操作 | 系统行为 |
| --- | --- | --- |
| 空闲时 | 输入并发送 | 根据上下文接续当前目标，讨论、读取材料、准备下一步 |
| 工作中 | 继续输入并发送 | 接收补充信息，立即显示“已收到”；明确它正在处理还是排在后面 |
| 工作中 | 停止 | 请求安全停止，保留已有成果，结束后说明保存了什么 |

“追加信息”使用同一个输入框和发送按钮，不再增加一个常驻按钮。
输入框不出现消息用途、阶段、验证方式、执行轮次和模型下拉。
模型选择移入设置；任务归档移入任务列表菜单；这些设置不参与普通对话。

Enter 发送、Shift+Enter 换行，保留 Ctrl/Cmd+Enter 兼容；中文输入法选字时
不能误发送。发送失败保留输入，刷新后保留已接收消息与未发送草稿。

每次阶段结果都按同一顺序回答：已经做成什么、还缺什么、接下来由谁做什么。
通常用两三个短段，必要时给一条查看详情的链接。当前只有一个明确待办时，
只推荐这一项；不要默认列出一整页可选操作。

授权仍然需要明确表达。确有必要确认时，在相关回复后展示一条短小的确认请求，
例如“按这个方案开始”或“创建草稿 PR”。它属于这次结果，不进入输入框工具栏。
不再要求用户先勾选、再复制授权文本、再选择消息用途、再点发送。
CLA 协议保留阅读协议、明确同意和亲自确认的专用流程。

**页面如何收敛**

任务页保留任务名称、一条当前状态、一列消息和底部输入框。
新消息直接出现在时间线上；方案、测试结果和 PR 预览以该条消息的简短内容呈现。
取消长期悬在消息末尾、随着轮询不断改变内容的方案与执行总面板。

| 当前内容 | 改造后的默认呈现 | 需要深入时 |
| --- | --- | --- |
| 完整方案表单 | 做什么、修改范围、怎样验证的简短说明 | “查看方案”；修改要求直接在对话里说 |
| 执行轮次选择器 | 当前进展或本次结果 | “查看历史记录”进入详情 |
| 文件列表、原始 diff、命令和证据 | “修改了 3 个文件，测试和代码检查通过” | “查看改动”打开详情视图 |
| 发布、更新文案、跟进、CLA 多个面板 | 只展示当前需要处理的一件事 | 用户提及时进入相应预览或协议阅读 |
| 过期的澄清按钮和确认控件 | 只读历史，标明当时选择或已失效 | 查看原始记录，不重新提交旧选择 |
| 内部错误和校验值 | 影响、已保留的成果、恢复办法 | “查看诊断”供排查使用 |

桌面详情使用单一侧边详情视图，手机使用全屏详情，并能返回原来的消息位置。
代码、测试日志和长协议放在详情中。主对话采用一条滚动路径，详情最多一层展开，
不再出现结果面板里套发布面板、发布面板里套多个设置区。

用户翻看历史时不要自动拉回底部；新结果用“有新消息”提示。输入框始终能发送
补充信息，运行状态不能让它退化成只能查看进度的入口。状态播报、键盘焦点、
详情返回和手机键盘遮挡都纳入可访问性验收。

**让系统承担推进工作**

后端增加统一的会话协调服务，复用现有规划、执行、审查、发布和跟进服务。
它负责把用户的一句话与当前任务状态结合起来，确定下一步，记录处理结果，
并在后台任务完成后主动产出一条可理解的回复。

| 用户说的话 | 应当发生的行为 |
| --- | --- |
| “先看看怎么改” | 读取必要代码并提出方案，等待执行确认 |
| “只改这个包” | 记住范围；有必要时修订方案，不再反复询问已回答的问题 |
| “现在到哪了” | 根据真实进度回答，不改变执行，也不要求切到询问模式 |
| “补充一下，还要考虑空字符串” | 立即接收并说明排队情况；判断是否影响已确认的方案 |
| “先停一下” | 请求安全停止，等待实际停止，再说明保留的结果 |
| “继续” | 在唯一、明确、仍有效的当前工作上恢复；存在多种可能时只问一个必要问题 |
| “没问题，准备发布” | 展示当前成果，按现有规则完成验收确认，然后准备 PR 文案与发布预览 |
| “标题短一点，全部英文” | 生成文案修订；发布前更新预览，发布后走现有独立更新确认 |
| “跟进一下 PR” | 读取 PR、项目自动检查与审核意见，说明现在轮到谁处理 |

“准备发布”授权的是准备工作。它不能直接变成 Fork、推送或创建 PR 的授权。
当前验收是独立记录时，由系统把它作为下一条明确确认呈现；确认后自动接上
文案准备，不要求用户再找生成按钮。首次发布仍只创建草稿 PR。

协调服务与模型的职责要分清：模型可以理解表达并提出下一步，服务端检查
状态、范围、预算和权限，再调用已有服务。普通文本、仓库内容和模型生成的
“同意”都不能成为受保护动作的确认凭据。

运行中追加的信息必须有可靠的接收和消费记录，不能只显示在浏览器内。
先支持每个任务一条有序的消息队列：问题可只读回答，补充材料排队进入后续处理。
收到、排队、已采用、需要重新确认分别有清楚回执。不要说“已经按你说的改了”，
实际却还没有被工作流程读取。

如果补充要求改变了已冻结的文件、命令、约束、依据或目标，先停止相应旧工作，
保存子方案并重新确认，不能直接改写正在执行的批准方案。用户无需选择“修改目标”
模式，系统在对话中解释这次调整为何需要重新确认。

暂停和恢复不能绕过现有修复与重试上限。普通失败在原授权和剩余额度内恢复；
额度用完时，说明已经完成的工作和需要的新决定，不让用户猜哪一个按钮有效。
环境暂不支持时说明产品缺少的能力；禁止把安装和测试转交用户在宿主机运行。
外部操作已发出且结果不明时，只核对结果，不能重复写入，也不能承诺停止即撤销。

**结果和术语如何表达**

默认界面只显示能帮助用户理解目标、评估结果和决定下一步的信息。
源码中的真实字段名、文件名和必要的项目术语可以保留；安全校验所需的内部
标识留在后台和诊断详情。不能用“指纹”“摘要值”替换“哈希”后继续要求用户
理解同一套内部机制。

| 当前表达 | 用户界面建议 |
| --- | --- |
| plan_hash / record_hash / binding_hash | 默认不展示，由后台校验当前内容 |
| 基线验证 | 修改前的测试 |
| Verify / Review | 测试与代码检查 / 独立代码审查 |
| Attempt 9 | 默认只说本次结果；历史中显示“第 9 次尝试” |
| Runner digest / policy version | 默认不展示，归入诊断详情 |
| stale / 批准指纹失效 | 代码或方案有变化，需要重新确认 |
| Fork、Push 并创建 Draft PR | 创建草稿 PR；预览用短句说明将使用你的账号上传改动 |
| CLA | 贡献者协议（CLA），附协议全文与明确同意入口 |
| CI 等待审批 | 项目的自动检查正在等待维护者批准运行 |
| Job succeeded | 按实际结果说“方案已保存”“测试已结束”或“测试通过” |

例如，代码完成后的回复可以是：

> 修复已完成，新增的两项回归测试通过。完整测试有 533 项通过、27 项跳过，
> 代码检查和独立审查也已通过。
>
> 你可以查看改动。确认结果后，我会按仓库要求准备英文 PR 文案，给你检查。

其中 533 是完整测试数量，两项新增测试已经包含在内，不能重复相加；27 项
跳过必须保留。五条验证命令全部通过也不能写成“项目所有检查全部通过”。

对当前已有 PR 的回复则应是：

> PR 已提交审核。上次检查时，项目的自动检查还在等待维护者批准运行。
> 现在主要需要等待维护者处理；你也可以让我再查一次最新状态。

成功、失败、停止、需要确认、环境不支持都由服务端状态生成基础说明；模型
补充必要解释。对外动作完成、测试通过等事实必须有对应结果，不能只依赖提示词。
新增回复不出现原始 JSON、整段校验值和后台路径。历史原文保持不变，可折叠为
历史记录，不为“去术语”重写旧消息或证据。

任务列表、标题状态和对话使用同一个用户状态投影。发布后的展示优先采用已有
可信远端观察，并显示观察时间；业务内部保留 `draft_pr` 不应让页面继续声称
PR 仍是草稿。远端读取失败时保留上次结果并说明未更新，不能制造新状态。

**确认操作如何简化而保持准确**

每次确认只对应一个当前动作，直接说明对象、影响和内容。确认控件由服务生成，
后台绑定当前方案或预览的确切版本、目标、代码、测试和审查结果。
确认后显示回执；重复点击不重复执行；内容变更、过期或跨任务使用都拒绝。

| 确认种类 | 用户看到什么 | 后台继续保持什么 |
| --- | --- | --- |
| 开始实施 | 修改范围、测试安排、自动修复额度，“按此方案开始” | 方案、代码、模型与环境的准确绑定 |
| 确认结果 | 修改摘要、真实测试和审查结果，“确认结果” | 当前执行和结果的验收记录 |
| 创建草稿 PR | 发布账号、目标仓库、完整标题正文、改动与测试入口，“创建草稿 PR” | 原有一次性发布确认和精确动作清单 |
| 更新 PR 文案 | 原文与新文案，“确认更新文案” | 只更新标题正文的独立一次性确认 |
| 转为正式审核 | PR、当前内容、会通知维护者的影响，“提交正式审核” | 现有独立 Ready 确认 |
| 签署贡献者协议 | 完整固定版本协议、账号、PR、声明，明确同意并确认 | 独立法律同意、精确绑定与不重复提交 |

创建 PR、更新文案、正式审核和签协议不能捆在一次“全部同意”里。
普通聊天中的“好”“继续”“看起来可以”不触发第三方写入。
确认控件直接调用独立确认接口，不把模型对聊天语义的判断当作授权。
本方案没有要求增加新的外部写入能力，也不需要取消现有安全约束。

**实施顺序与代码落点**

每个切片都应交付前后端联通的可用行为。不能先删除模式选择，再让同一个输入框
仍然走只能解释状态的通道；也不能先加入意图识别，却继续让用户使用旧面板找入口。

| 顺序 / 拟议任务 | 交付内容 | 主要位置 | 完成条件 |

最小首批应完成 1、2，并让当前任务的“跟进 PR”和一个尚未实施任务的
“讨论 → 确认 → 自动执行 → 收到结果”可用。随后补齐 3–5，再做完整验收。
首批上线不能宣称整套改造已经完成。

保持 FastAPI、SQLite、原生 HTML/CSS/JavaScript、现有模型接口及隔离 Worker。
不需要更换前端框架、把业务状态交给模型或合并 Publisher 与执行环境。

新增消息排队、当前确认、消费回执等持久契约需要明确版本和前向迁移。复用现有
事件表时也要定义新的事件契约与恢复规则，不能把关键状态放在前端变量里。
旧的 `mode` API 在过渡期保留兼容，新 UI 不依赖它；新请求与响应、原生调用和
契约测试同步升级。旧历史、方案批准及证据保持原样，无法证明的新关联不回填。

实施前备份一致的 SQLite 与制品。升级测试覆盖现存任务和历史；回退前排空新消息
队列、处置未确认预览并核对已发出的外部操作，再使用匹配代码与数据恢复。
每个代码切片完成相应测试、凭据检查和部署健康检查，不能仅凭新界面截图验收。

**如何证明改造成功**

默认离线测试验证状态、授权、消息消费和恢复；真实浏览器验证完整交互。
真实模型与沙箱验收另外记录，不能以模拟响应代替。

| 验收场景 | 必须观察到的结果 |
| --- | --- |
| 普通用户从新任务开始 | 仅通过项目内对话、查看详情和上下文确认完成方案、实施、真实测试、独立审查及 PR 准备 |
| 本任务回放 | “没问题，准备发布”进入准备流程；不能只回答没有权限，也不能直接发起发布；已有 PR 则接续发布后工作 |
| 运行中追加两条信息 | 顺序、接收和消费状态准确；不丢失、不重复、不偷偷修改批准方案 |
| 问进度与改目标 | 问进度不停止工作；改目标解释影响并进入修订确认，不需要用户选模式 |
| 停止与服务重启 | 真实安全停止、保留结果；刷新和重启后仍能知道在等谁、怎样继续 |
| 失败与额度耗尽 | 自动恢复仅使用原授权和剩余额度；不能循环重试、隐藏失败或让用户改数据库 |
| 发布前后 | 发布账号、PR 内容可读；模糊同意不写 GitHub；未知写入结果只核对；不能重复创建 PR 或重复签名 |
| 状态一致性 | 列表、任务顶部与对话对草稿、正式审核、等待维护者的表达一致，并注明远端观察时间 |
| 简洁与可访问性 | 输入框零用途/模型下拉，默认无内部校验值；主对话无嵌套工作台；桌面、手机、键盘与中文输入正常 |

对当前任务先做只读状态与交互回归，不重跑已发布贡献或重复写入。
新建专用非生产 Python 与 TypeScript 任务验证真实执行；外部发布验收只使用
专用测试账号和草稿 PR，并在确切预览后由人逐次确认。复杂环境未支持时如实阻断。

每次真实验收记录：用户为了操作流程而点击或切换了什么、是否求助外部 Codex、
是否需要终端或数据库干预、失败阶段、恢复次数、模型预算、真实测试与审查结果。
正常路径与故障恢复路径分别记录。

完整通过标准：两类支持环境的任务均能只在产品中完成；外部 Codex 补操作、手工
改数据库和用户本地执行上游代码的次数为零。用户表达目标、回答必要问题和确认
具体外部动作属于正常参与，不算系统失败。一个任务成功只能作为个案证据。
