# 工作流架构评审（2026-10-09）

结论：存在跨候选的结构性可靠性问题。当前把丰富报告的生成格式、
业务流程准入和执行安全混在同一组强制条件里。后续应优先重构这些边界，
继续复用 FastAPI、SQLite、原生界面、持久任务、产物和沙箱基础设施。
本文件是评审及改造建议，未授权外部写入，也未实施新的状态或数据库模型。
Phase 5 保持当前阶段；P5-G06 仍是下一项路线图验收。

**实际证据及边界**

- 最近 100 条 Job 中有 19 条 `provider_analysis`，其中 16 条最终失败、
  3 条成功。16 条失败错误码均属于结构化报告或引用契约类。这是包含修复前
  历史和不同任务的观察样本，不能用作当前适配器的上线失败率。
- 329 在旧格式下有三个失败 Job、四次失败尝试。新 Job
  `0abaca53-381c-40d6-bf46-f52a76fa25ba` 在修复过程中经过两次失败，
  第三次生成了可验证 AnalysisVersion。这只证明一次评估成功。
- 当前没有候选 329 的 ContributionTask；现有一个任务是 Oppia 的
  `9727c1c6-04d4-4422-a8b0-e47b61517816`。因此尚无 329 从评估、
  规划、修改到真实测试和审查通过的完整证据。
- `analysis_schema.py` 的当前契约有 20 个必需顶层字段，并要求逐字段引用；
  七类列表需要对应引用行。`analysis_wire.py` 改善了列表配对，持久报告的
  复杂契约与流程前置关系仍然存在。
- `ContributionTaskService.create` 要求已有 AnalysisVersion。
  当前没有独立于完整报告的最小评估依据和只读讨论入口。
- `PlanningReply` 要求提问、读取文件和生成方案三种结果互斥；组合结果
  会触发 `planning_outcome_conflict`，整个回合失败。
- `environment_plan` 只识别指定根目录清单，混合 Python/Node 会阻断；
  Node 依赖要求 package-lock，Python 要求带哈希的 requirements 文件。
  “改动小”“语言匹配”和“当前环境能验证”是三个不同属性。
- `Job.succeeded` 只表示对应任务完成。真实测试通过、审查通过和完整工作流
  成功必须分别验证。WB-G03、CX-G02 等真实执行验收仍未完成。

**约定应如何处理**

| 约定 | 处理建议 |
| --- | --- |
| 令牌隔离、沙箱、网络/资源限制、批准范围、过期授权、输入及产物哈希 | 保留硬阻断；只在涉及相应操作的边界检查 |
| 正式评估依据中的事实及引用可追溯 | 保留；无法支持的判断保持未知，不制造引用或事实 |
| 丰富评估中的工作量、竞争、赏金说明、维护者问题等全部字段齐全 | 从流程准入移入可选报告质量层；缺失明确显示未知 |
| 引用总索引、平行数组对齐等机械结构 | 由服务器从同一条带引用的结论生成；不要求模型重复维护 |
| 任一非关键报告字段异常使整条流程无法开始 | 保存合法的最小依据；不完整材料只作为明确标注的只读草稿 |
| 一回合只能提问、读文件、给方案之一 | 分开自然语言回复、工具请求与方案草稿，由协调器按确定顺序处理 |
| 生成报告即视为具备实施条件 | 执行前必须有仓库、环境及基线验证的真实结果 |
| 格式错误后原样调用同一大提示词 | 返回字段级脱敏诊断；确定性修复仅处理已定义的无歧义格式差异，必要的模型修复必须有独立且累计的预算 |

任何不符合正式 schema 的材料都不能成为可信 AnalysisVersion 或执行授权。
只读草稿需要独立、可验证的草稿契约，经过敏感信息检查和安全渲染；敏感输出
不保存正文。未知引用、缺失关键依据、非法命令和哈希不匹配仍拒绝。
不允许用“补默认值”虚构引用、测试结果、审核结果、工时或批准。

**建议的最小改造切片**

1. 将评估分成最小可信依据与可选丰富报告。最小依据记录准确的 Snapshot、
   需求事实及来源、未知项和版本哈希；可选报告用于解释投入和建议。
   正式链仍为 Snapshot → AnalysisVersion → Approved PlanVersion →
   ExecutionAttempt → ReviewRun；不跳过任何正式授权及来源记录。
2. 对话先支持安全读取代码、讨论和静态环境检查，再冻结可执行计划。
   自然语言、工具调用和方案数据采用各自的小契约。只有执行计划需要严格
   完整的路径、命令、版本及批准；普通交流不会因报告展示字段不全被丢弃。
3. 将可验证性检查提前。静态识别环境后，在沙箱里用相同命令运行修改前
   基线，再实施修改并运行修改后验证。依赖仍通过独立、无凭据、受限代理
   准备。环境不足应能在对话中说明和恢复，不靠反复改方案解除。
4. 每个修改阶段能恢复、能取消、能保留真实结果。展示阶段、阻断原因和
   可采取的下一步；阶段完成、测试通过和最终成功分别显示。

持久模型或正式分析结构变更必须提供新版本、前向升级、旧历史读取测试和
回退/恢复说明；不得编辑历史记录或已批准方案来兼容新流程。该方案不需要
更换前端框架、数据库或合并现有信任域。

**验收应改成可重复的真实任务**

- 先选明确支持环境的非生产 Python、TypeScript 小项目和文档修复，逐个完成
  创建任务 → 对话讨论 → 批准计划 → 实际 diff → 真实测试 → 独立审查。
  模拟响应和一次评估报告成功不能替代这些证据。
- 对选定样本重复运行，记录首次成功率、格式修复次数、人工介入、模型调用
  预算和失败阶段；明确区分历史统计与最终版本统计。
- 注入可选报告字段缺失、引用缺失、环境不足、取消和服务重启。非关键材料
  缺失不阻断只读交流；安全及授权失败始终阻断相应操作。
- 保留旧 Oppia 任务作为复杂环境的恢复用例，不将其充当尚未支持环境的
  “简单任务”验收，也不通过宿主机运行或开放任意安装来绕过隔离。
- macOS/OrbStack 与原生 Linux/Docker 的平台验收分别记录。发布仍需针对
  精确目标、diff、测试、审查及动作的一次性用户确认。

当前建议优先交付第一、二步和一个真实小项目的完整链路，再扩展环境覆盖。
这次评审未新增代码、发起模型评估、执行仓库代码或修改外部状态。


**本轮实施（2026-10-09）**

用户已授权结构调整。第一切片实现最小事实评估与可选 AI 报告分离，并拆开对话意图
和严格方案校验：快照入口生成 schema 2 AnalysisVersion；显式零模型用量与空调用引用，
不伪装 AI 成功、不制造 Top 30 排名、结论、工时或批准。schema 1 报告及其成功 Job、
调用约束保持不变。讨论依据仍须验证真实 Snapshot/Score 的内容哈希与来源。
`0033_snapshot_assessments` 含前向迁移、旧报告/任务/计划读取检查和恢复指引。

规划处理顺序为澄清 → 安全读取 → 保存完整方案。纯文字回复可以完成对话；
格式或领域校验失败的草稿仅保存脱敏诊断与有效说明，不创建 PlanVersion。
组合中的方案在澄清/补读完成前不保存、不批准；未读现有文件自动加入有限读取请求。
不再静默删除变更路径、截断命令或移除未决问题。非法路径、凭据、过期依据及执行授权
继续在对应边界拒绝。可选报告故障不会影响已经冻结的任务讨论依据。

静态环境诊断继续在代码读取后、执行批准前展示。修改前真实基线与修改后相同命令比较、
更多环境适配、重复真实模型完整执行及原生 Linux 验收仍需独立实现/验证，不能由本切片
或一次对话成功代替。具体验证证据在 `docs/tasks.md` 的 WD 条目维护。

验收补充（2026-10-10）：拒绝草稿只阻断其后的执行确认；用户通过严格校验保存的新计划版本可解除旧草稿错误，历史拒绝记录和旧计划哈希仍保留。真实候选 325 已完成隔离读取和两轮模型讨论，发现当前源码已包含需求链接，以普通对话结束核查，没有制造空改动或执行批准。完整执行验收仍独立待办。
