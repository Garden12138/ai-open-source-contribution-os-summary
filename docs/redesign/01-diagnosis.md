# 01 · 需求重述与现状诊断

> 结论：**需要重新设计**。失败的根源在核心抽象（自研 Coding Agent + 全链路哈希授权治理），
> 而不是某个参数或某个模块的缺陷；继续在现有结构上修补，只会重复过去两个月的循环。

## 1. 需求重述

用户原始诉求只有两句话：

1. **发现**：找到值得投入的开源贡献机会（有赏金的、高影响力的、技术栈匹配的）。
2. **贡献**：在平台上通过对话，把一个机会推进到最终贡献（PR 提交到上游）。

把它展开成产品目标：

| 目标 | 用户能感知到的结果 |
| --- | --- |
| G1 发现 | 每天打开就能看到一份有理由的推荐清单，也能粘贴任意 Issue 链接直接开始 |
| G2 对话贡献 | 像用 Codex / Cursor 一样，在一个对话里让 Agent 读代码、给方案、改代码、跑测试；随时补充要求、停止、继续 |
| G3 安全发布 | 只有在我看过改动和 PR 文案、点了确认之后，才会在 GitHub 上出现 Draft PR |
| G4 记录 | 能看到我提交过哪些 PR、状态如何，形成贡献履历 |

隐含但关键的非功能需求：**不中断**。一次贡献通常需要几十到上百次工具调用、
数十分钟，期间任何一次模型抖动、网络错误、服务重启都不应让任务"终态失败、
需要重新审批"。

## 2. 现状盘点（截至 2026-11-13，分支 `feature/upgrade-chatgpt`）

| 指标 | 数值 |
| --- | --- |
| 应用 Python 代码 | 246 个文件 / 78,159 行 |
| 测试代码 | 217 个文件 / 51,097 行 |
| 文档 | 41 个文件 / 34,773 行，其中 `docs/tasks.md` 7,339 行、事故复盘 20,800 行 |
| 前端 | 原生 JS/CSS 约 11,000 行（`app.js` 4,970 行） |
| 数据库 | 47 个迁移、约 45 张表 |
| 运行服务 | API、Worker、Provider Worker、Model Gateway、Sandbox Worker、Publisher 共 6 个 |
| 提交历史 | 134 个提交，近期绝大多数是 `docs(...)` 归档验收失败和"精确预览" |

规模本身不是问题，问题是规模花在了哪里：发现与评分（Phase 1）只有约 1,500 行，
而围绕"自研 Agent 循环的预算、批次、续读、容量证明、授权绑定"的代码和文档占了绝大部分。

## 3. 实际效果

**真实任务从未在没有外部维护的情况下完成过一次贡献。**

- 截至 10-27：9 个任务、2,241 个事件；4 个 Draft PR 均有外部 Codex 介入修平台、恢复任务。
- 10-28 Runtime v2 重构后：两个试用任务（radashi #257、more-itertools #1316）都在编码前失败
  （修改前检查的工具缺失 / 动态安装 / 只读缓存）。
- 11-03 至 11-09：同一个 Issue（`patoles/agent-flow#107`）先后创建了 **Plan10 → Plan16 共 7 个方案版本**，
  每次都要冻结、精确预览、人工逐字授权，**产出补丁数为 0**：

| 运行 | 停止原因 |
| --- | --- |
| Plan10 | 模型一轮请求 5 个工具，超过 4 个上限，整批拒绝；纠偏额度耗尽 |
| Plan11 | 14 次模型调用、39 次读文件（6 个文件全部从偏移 0 重复读）→ `agent_budget_exceeded` |
| Plan13 | 模型读取一个计划中"待新建"的文件 → `source_unavailable` 终态 |
| Plan14 | 8 个大页读取的"输出容量上界"超过剩余预算 → `agent_read_batch_budget` 终态 |
| Plan15 | 第 15 轮 4096 输出 token 全部被推理占满 → `deepseek_completion_truncated` 终态 |
| Plan16 | 模型网关的凭据库变成空文件 → `model_gateway_internal_error`，重试耗尽 |

- 环境引擎（UPEVE）泛化：首次 Baseline **0/15**；原生端到端交付 **0/4**。

## 4. 根因

### R1 自建了一个 Coding Agent，并且把它"饿死"了

现象：模型反复读同一批文件、截断、超批次、超预算。

证据：自研循环的硬限制是 **单次请求 32,000 字节（约 8K token）**、**单次输出 4,096 token
且开启高强度推理**、**每轮最多 4 个工具调用**、读取/写入/检查各自独立计数。
成熟的 Coding Agent（Codex、Claude Code、OpenHands）使用 200K 以上的上下文、
自动压缩、每轮不限工具数量，单个任务几十到上百次工具调用是常态。

为什么是根因：在 8K token 的窗口里，模型看不完一个中等文件加任务描述，
只能反复重读（Plan11 的 33 次重复起始读取就是这个症状）；4,096 输出被推理吃满
就必然截断。每一次"修复"都是在这个错误前提上再加一层预算/容量证明，
复杂度单调上升，能力不变。**这不是调参能解决的问题——平台不应该自己造 Agent。**

### R2 治理机制压倒了产品

现象：任何小失败都变成"终态 + 授权已消费 + 需新 Plan + 新精确预览 + 人工逐字批准"。

证据：`AGENTS.md` 要求每一步消费上游的不可变 ID 和哈希，任何冻结输入变化都会让下游
授权失效；`tasks.md` 中单个条目常见 20 个以上的哈希。HR4 一节里，为了一次真实执行，
要核对源码集合哈希、Binding 哈希、Revision、Preflight、预览哈希、授权哈希……

为什么是根因：把 Agent 的每一步都当作需要法律级证据的动作，导致"继续"在系统里几乎
不存在——这正是"对话中执行就中断"的直接来源。对单用户本地工具来说，真正不可逆、
需要人确认的只有一件事：**对第三方 GitHub 的写操作**。容器里的读、改、测都可以随时丢弃重来。

### R3 "断网验证 + 冻结依赖配方 + 自研环境推导"成为最大的失败面

现象：pnpm 动态安装、Vitest 只读缓存、`ruff`/`stubtest` 不在 PATH、DNS、原生 addon……
每个项目都要平台补一个适配器。

证据：`sandbox_worker/dependencies.py`（1,879 行）、`environment_engine/`、
`package_dns.py`、`node_cache.py` 等；泛化 0/15。

为什么是根因：真实开发者（以及成熟 Agent）在容器里直接 `pip install` / `pnpm install`，
失败了看报错再处理。要求平台事先推导出可在断网环境下复现的依赖配方，
等于要平台替所有项目解决构建问题。

### R4 本地单用户场景拆成 6 个服务和多个信任域

现象：运维故障直接打断任务（Plan16 因网关凭据库丢失而失败）；部署要处理管理密钥、
readiness 密钥、Store ID、签名密钥、Publisher 密钥等。

为什么是根因：同一台机器、同一个操作系统用户下的多个进程互相隔离，几乎不增加实际
安全性；真正的边界是"宿主 ↔ 容器"和"凭据放在哪里"。多出来的进程只增加故障点。

### R5 对话是状态机的外壳，不是 Agent 本身

现象：意图路由误判、模型说"开始实施"但什么都没发生、"继续"被接收却没排入下一步、
澄清回答要绑定 `question_source_hash`。

为什么是根因：用户想要的是"像普通代码 Agent 一样只有发送和停止"（C02 原话）。
成熟 Agent 的线程模型（消息 → 一轮工作 → 流式事件 → 可插话/中断/继续）天然满足这一点；
平台在外面再套一层意图分类和阶段状态机，只会制造不一致。

### R6 开发流程本身放大了问题

现象：Codex 会话越来越长、经常中途中断；产出偏向文档和证据归档。

证据：`AGENTS.md` 14 KB，要求每次改动后重部署、canary 扫描、更新 7,000 行的 `tasks.md`、
记录平台门禁；近 30 个提交中多数是 `docs(agent): archive ...`。

为什么是根因：每个 Codex 会话的上下文和时间大量花在读治理文档、补证据上，
真正写功能的份额很小；规则越多，Codex 越倾向于"停下来请求精确授权"。

## 5. 为什么不能继续修补

- 自研 Agent 循环与 Plan/Approval/Binding 哈希链是数据模型的主干：47 个迁移、
  几乎所有表都围绕它。替换 Agent 引擎必然要拆掉这条链，等于重写，而且是在旧结构里重写。
- 环境引擎、预算体系、容量证明都是为 R1/R3 的错误前提服务的，换成成熟 Agent 后整体失去意义。
- 旧文档和规则会持续把 Codex 拉回旧范式（例如"验证必须断网"、"API 不得持有 Docker"）。

因此建议：**保留发现模块和少量通用工具，其余以新架构重建**；旧代码打标签归档，不迁移旧任务数据。
