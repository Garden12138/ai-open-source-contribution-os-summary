# 通过对话完成贡献任务

日常操作集中在一个输入框：发送要求、补充信息、停止。助手完成一轮工作后，
会说明已完成的内容、遇到的问题和下一步。Enter 发送，Shift+Enter 换行；
未发送的草稿保存在当前浏览器标签页，刷新后保留，发送失败可重试。

2026-10-24 的任务运行时支持交替询问进度、追问详情和执行下一步。进度查询
不调用模型，也不替换先前讨论对象；可点击“询问这条结果”精确引用历史消息。
引用与草稿一起跨刷新保存，失败重试沿用相同完整内容和请求标识。新任务与
下一次空闲时收到 API 消息的旧任务使用新版；运行中的旧作业保留原协议。
只读消息仍会显示为待回复，但不会阻止后台工作或使当前澄清问题失效；
未分类消息、变更要求和停止仍保留动作屏障。继续操作依照真实任务状态和
原确认执行，不依照最近查看的历史版本执行。详细状态、预算、迁移及回滚见
[对话任务运行时](agent-runtime.md)。

助手提出带选项的澄清问题时，每题可点击选择一项，也可填写自定义回答。
默认不替用户选择；全部问题答好后点击一次“发送回答”，把问题与对应回答
合并为一条用户消息，沿用对话收件、同源/CSRF 与幂等处理。选择时不发送请求，
不清空输入框里另写的草稿。选择绑定当前任务和提问消息，刷新后保留，失败后
可用同一个请求标识重试；合并文本仍须满足 8000 字上限。
已回复或已被新问题替代的选项只作历史显示；暂停、繁忙或待处理时不可提交。
这些回答仅用于方案讨论，执行、发布及法律同意仍须走各自独立确认。
批量选项请求另带 `question_source_id` 与 `question_source_hash`，服务端在同一事务
核对本任务最新提问、空闲规划状态及尚未回复的依据。接收记录保存原问题关联；
协调器再次核对后直接继续原方案讨论，先完成此前暂缓的补读，不使用模型进行
意图判断。过期问题和不同幂等请求的重复回答拒绝；同一请求可返回原收件记录。
两项关联字段须同时提供；普通文字消息保持原协议和对话推理流程。

规划模型返回结构错误时，先拒绝该输出，再在原有最多两轮修订额度内提供具体
字段诊断并要求重新返回完整的 `reply/questions/read_paths/plan`。顶层误放方案
字段和字段类型错误不会直接转换为已保存方案。敏感原文在解析前拒绝，不进行
这类自动纠正；被拒绝的结构输出用量计入原有累计讨论预算。

方案、改动与测试、发布预览使用同一个详情抽屉。桌面侧边显示，手机全屏显示，
Escape 关闭并返回原来的位置。历史记录保留原始证据，默认对话不展示内部校验值。
模型选择放在设置页；已有任务可在空闲的方案讨论状态单独调整模型，调整后需要
重新生成并确认方案。

实施转入验证时，阶段变更与任务入队在同一事务中完成。重复调度和中断恢复
沿用同一个验证任务及批准命令；排队、运行或等待入队的验证环境不会因协调器
暂时受阻而被回收。旧版本已回收依赖、导致验证无法启动时，在原授权仍有效且
输入未变的前提下，可在既有验证次数预算内恢复：重新隔离准备相同环境配方，
对原冻结源码重跑基线，追加新环境和基线收据，再用新的验证输入版本验证原有
改动。原方案授权、改动、工作区和失败哈希保持不变；停止、过期或配方变化、
恢复基线失败及预算耗尽均停止恢复。新环境不冒充旧依赖哈希，也不授予发布权限。
协调器异常另存不含异常原文及参数的位置诊断；无关联任务的旧环境诊断不再
覆盖当前错误。
若本机 DNS 把既有包白名单域名改写到测试网段，代理继续拒绝连接该地址，只对
这些固定域名使用经 TLS 验证的固定 HTTPS DNS 端点，并重新校验公网地址及
问题/CNAME 关联。真实公网解析和代理 TLS 证据通过后，才能解除对应任务的
历史传输诊断并在原次数预算内分配新准备任务；其他准备失败不因此解除。
恢复环境后仍照常执行真实测试和独立审查。代码检查失败不等于基础设施再次
失效；两轮自动修复用尽后，保存失败证据、准备修订方案，新的执行需单独确认。

## 正常流程

1. 说明目标，助手整理方案。需要调整时直接补充要求。
2. 查看方案并点击“按此方案开始”。助手实现、测试并安排独立审查。
3. 查看改动与测试后点击“确认结果”。助手读取仓库规范，生成英文 PR 文案并准备预览。
4. 核对完整预览后，单独确认发布 Draft PR。
   发布成功回复直接包含已核对的 PR 地址链接；旧成功回复也从原发布记录补充显示
   链接，保留原始会话事件，不重新调用发布或模型。
5. 发布后可说“跟进 PR”“调整正文”或“准备提交正式审核”。助手读取状态或准备
   新预览；修改远程内容和提交正式审核仍需分别确认。

新建任务不会自动读取仓库。可以发送具体要求，或点击“读取仓库并准备方案”开始。
读取状态区分尚未开始、后台排队、正在读取、失败、超时和停止；失败后发送“继续”
可重新准备，保留已有记录。该入口只准备方案，实施仍须点击“按此方案开始”。

处理顺序为：下载完整源码归档 → 阅读项目说明、规范、清单和相关代码 → 准备方案
→ 用户确认 → 隔离依赖准备与修改前测试 → 实施 → 离线验证 → 独立审查。
源码下载和静态阅读不需要安装项目依赖；依赖适配只限制实施和验证。
没有方案时不根据文件名提前判定执行环境不支持。已下载归档不意味着所有文件都
进入模型上下文：系统先概览项目，再按需补读。清单中没有对应阅读记录的文件是
尚未读取；明确标记内容不可用的文件须保留安全限制。

规划的自动概览保持单文件 256 KB 上限；显式补读可让单个文件使用既有 700 KB
总阅读预算，原文与完整 SHA-256 一起校验。模型明确请求的目标文件保留全文，
背景文件可压缩为骨架。总输出、隔离策略、敏感内容过滤与实施阶段的独立限制
继续生效。用户回答范围澄清后，先补读之前暂缓的合法路径，再继续规划。
源码是否已获取这类状态问题直接使用持久记录回答，不由模型猜测依赖原因。

执行前还须通过 `execution-capabilities-v3` 检查。页面、执行确认接口和后台
使用冻结文件原文及同一元数据校验函数；仅存在 `pyproject.toml` 不代表环境受支持。
检查涵盖动态依赖、清单原文/哈希、未适配的依赖声明、实施文件和上下文预算。
缺少清单时，规划先补读；已知不支持时仍可保存方案和讨论，但不显示执行确认。
直接调用确认接口同样拒绝，且不生成批准、执行或作业。检查通过只表示适配器
接受这些输入；真实安装、修改前测试和后续验证仍各自需要成功证据。

新执行授权绑定检查结果哈希与能力版本；后台在接触 GitHub 或创建执行前重新
核对，变化时拒绝旧授权。已受阻任务显示受阻，持久保存失败原因和失败作业。
准备条件不满足时发送“继续”不会重复启动、自动改方案或放宽测试；可恢复的模型
子任务仍沿用原有冻结输入、次数限制和恢复规则。

Salt 任务 `86b6be40-2022-4975-ab04-2d56f1cc0f17` 暴露的动态依赖使用
`workspace-dependency-plan-v3` 隔离 wheel 元数据适配；测试清单也作为冻结输入。
`coding-context-v2` 允许单文件 700 KB，完整原文哈希和精确编辑保持不变，总预算
仍为 1.5 MB；旧 v1 上限仍是 256 KB。两个适配已通过真实沙箱夹具验证，但不能
代替 Salt 任务本身的安装、测试和审查验收。2026-10-14 后续真实失败进一步确认
`timelib` 没有当前 Linux/Python 的 wheel。用户同意新增独立断网源码编译能力，
通过可选 `DEPENDENCY_BUILDER_IMAGE` 启用 `workspace-dependency-plan-v4` /
`source-wheel-v1`，旧策略仍为 wheel-only。新的能力检查与批准绑定编译镜像。
编译器仅能读取必要输入，在有配额的临时空间运行；wheel 经有界传输交给可信
离线导入器。构建工具、源码、编译产物和失败诊断均保留哈希依据。

这条任务的冻结 Salt 源码先通过新策略准备依赖，原有两份 pytest 文件共 7 项
修改前测试通过，并保存待批准方案 v3。用户随后批准 v3，实际执行已完成拼写
修复、修改后 8 项测试及独立审查；用户已确认结果，后续英文文案与发布预览也已
准备好，尚未发布。失败时显示明确
阶段与包名，不保存原始包输出；相同
冻结环境已有确定失败证据时，改写方案也不能绕过执行准入。

修改草案先整体校验格式、批准范围、冻结文件哈希和原文精确匹配，再交给隔离
实施。任一操作无效都拒绝整份草案，不跳过坏操作应用其余部分。原文不存在、
匹配不唯一、格式或哈希错误可在当前持久 Job 的原次数额度内修正；不增加批准、
执行尝试或模型预算。越界、敏感内容和超限输出直接拒绝。修正前重新核对租约、
取消、停止、方案和对话绑定，运行期间续租，失效时不重新排队。

失败保存 `proposal-rejection-v1` 制品及 `proposal-validation-v1` 诊断，记录模型
用量、上下文/对话哈希、失败位置、匹配数与原文片段。敏感或超限原始输出只留
哈希，不保存正文；页面和错误日志不回显原始异常。再次调用仅接收同一 Job、
上下文和对话绑定的有限失败草案与诊断，片段只用于重新生成草案，不能授权模糊
替换。讨论阶段没有文件修改工具，“已编辑”之类模型叙述不构成实施证据；实际
改动以隔离 Worker 结果为准。Salt 的首次旧失败没有保存模型输出，不能事后推断
当时具体用了哪个错误锚点。恢复沿用用户已批准的 v3 和原执行尝试，第三次模型
调用修正成功；测试及审查通过后停在结果确认处，未自动验收或发布。

运行时可以继续补充信息。修改目标会先安全停止当前工作，再产生新方案；
旧方案的批准不能用于新目标。说“停止”保留已有成果和未处理信息，说“继续”
恢复处理。已经确认并开始的远程发布操作需要先核对实际结果，不能用停止按钮撤回。
协议签署须阅读协议并亲自勾选同意，聊天内容不能代替法律同意。

## API 与持久化约定

新入口为 `POST /api/v1/tasks/{task_id}/workbench/conversation/messages`，请求体
普通请求为 `{"text":"…"}`；批量选项回答同时提供上述两项提问关联字段。
两种请求都要求现有本机访问授权、同源/CSRF 检查及 `Idempotency-Key`。
成功返回 202 和 `message_id/status/text`；重复提交相同请求返回同一收件记录，
同一个请求标识对应不同文字时拒绝。消息上限 8000 字，待处理消息最多 20 条。

工作台查询新增 `conversation` 投影：`version`、`messages`、`results`、
`pending_count`、`paused`、`user_state` 和 `pending_action`。
`pending_action` 只提示下一步，不授予执行或发布权限。列表和对话使用同一状态
解释；发布后显示最近保存的远程检查状态及读取时间，不冒充实时数据。

持久化协议为 `conversation-v1`，复用现有追加式工作台事件和持久 Job，
不新增表、不改写旧事件、不补造历史关联。收件、分类、派发、用量、结束、暂停、
恢复和结果都有版本与稳定关联。结果绑定来源事件或 Job/尝试；重启后协调器继续
处理，即使浏览器已关闭也会生成结果，重复协调不产生重复回复。
只有开始使用新对话的任务参与新结果处理，升级或只读查询不会改写旧任务。
不认识的事件版本拒绝继续，须恢复匹配版本。

普通补充按顺序派发；读取进度的问题可以先回答。新的非控制消息使用
`conversation-reasoning-v2`，通过既有供应商接口生成自然语言回复、按需读取证据
并提出受限工作流调用，不再只返回一个分类词。上下文包含最近 12 条双方对话、
当前方案/执行/验收/账号状态、成果索引，以及当前已准备文案或预览的完整公共
标题和正文。发布后默认改为读取已保存的 PR 地址与状态；有待确认的审核预览时
读取该审核预览，创建草稿时的预览只作为历史材料。对话与工具输出均有字节上限，
不能声称已读取被截断的完整原文。

工具可读取本任务方案、diff、测试、独立审查、文案、发布/审核预览、已保存 PR、账号和已经读取的
冻结源码片段；不能指定任意制品 ID、其他任务、URL、宿主机路径或命令。源码
工具支持固定原文中的字面检索和有界行范围；未读文件明确返回不可用。每轮最多
两次模型调用、三份证据读取，包括格式纠正、工具读取后回复和取消后恢复，与
规划共用累计模型预算。工具结果保存在有哈希的制品中，重启沿用剩余额度。

普通回复直接采用模型对当前问题的回答。需要准备或修改时，模型只能选择当前
状态可用的一项工作流；服务端重新核对方案、成果、账号和停止依据，再调用原有
服务并传递用户原始要求。模型解释不能代替实际 Job 成功。执行、验收、发布、
更新远程正文、转为审核和法律签署的确认均不在工具列表中，仍只能走独立确认。
不完整 JSON、未知操作、错误引用和过期操作依据均不派发。

四个回复字段（`reply/action/reads/references`）均在传输 schema 中明确为必填；
跨字段约束由服务端独立校验，不能依赖供应商仅返回合法 JSON。Studio 传输层只
对 Inspect/Analyze 注入分析引用规则；普通对话和文案任务按各自 schema 与语言
要求处理，不能混入分析阶段的引用 ID 或固定中文输出要求。无效决策保留安全的
`conversation-decision-rejection-v1` 制品、字段位置和模型用量，原两次额度内使用
具体反馈纠正；敏感原文只留哈希。协议失败明确说明未派发，不归咎于用户表达。

用户要查看已有预览时，回复引用其固定来源，页面直接展开完整标题和正文，并
提供原预览入口；过期预览仍可阅读，不能授权发布。查看不重新生成文案，不
进入“已有 PR 转为正式审核”。标题状态也区分结果已确认、文案已准备和预览过期。
准备工具具有复用语义：已有预览时返回已有成果，包括已过期但可读的预览；
已有文案而尚无预览时直接准备该文案的预览。更新过期预览使用独立的
`renew_publication_preview`，只更新当前预览中固定文案的预览；改写文案使用 `revise_document`。
“创建草稿 PR”是推进发布流程的请求：预览过期时可以先沿用原文案重新准备，
预览有效时直接展示确认入口；两者均不能用聊天代替最终发布确认，也不能把助手
先前提出的可选文案建议变成新的必填条件。只查看预览仍不会更新它。
完整预览抽屉明确显示按钮不可用的原因；过期时出现“沿用文案更新预览”。按钮
调用 `POST /api/v1/tasks/{task_id}/workbench/publication/renew`，只提交
`{"preview_hash":"…"}`，使用既有访问控制、同源/CSRF 和幂等键。服务器锁定并核对
当前预览、账号、结果验收、文案与独立审查，创建只读的持久准备作业。它重新检查
上游与仓库规范，生成新有效期和一次性确认值，原标题正文不变；旧确认继续失效。
相同幂等请求返回原作业，新请求引用旧预览则拒绝。过期期间抽屉保持打开也会显示
恢复入口，待处理对话、暂停与繁忙状态都有对应提示。新预览仍需用户重新核对。
模型上下文明确列出本轮可引用的已读证据名称，错误引用的纠正诊断返回可用列表；
未读取的账号等证据仍不能冒充已读取，不通过放宽引用校验修复失败。
现有成果上的更新提议须在原两次调用内先核对用户请求的实际效果，不能把“已
过期”当作用户请求重新生成。即使模型误选“准备”，服务端也不能重复生成已有成果。
已排队且没有新版本标识的旧分类 Job 保留原协议；旧事件和两次错误回复不改写。

## 固定资源下载授权

Supported frozen projects expose `native_resources` in the workbench projection.
The conversation shows a resource request with its purpose; the preview drawer
shows the exact GitHub Release URL, version, platform, SHA-256, download/extraction
limits and expiry. The user presses “授权下载这些资源” to confirm that exact preview.
Chat, model output and old execution approval cannot authorize a resource download.

Preparing a preview performs no download. Confirming queues one durable resource
job; repeated confirmations return the same job. Expired, changed, stopped or busy
inputs fail closed. Failure retains the plan and permits a fresh preview/consent.
Download consent does not approve implementation or publication. Ready resources
change the frozen environment; execution still requires its own confirmation and
pre-change tests. Verify remains offline with fixed read-only resource paths.

当当前方案可执行时，对话底部显示“核对方案并继续”，资源就绪提示后也保留这一
明确入口。打开详情只展示当前方案；核对范围和测试安排后，用户在详情中点击
“确认方案并开始”，沿用同一个精确执行授权接口。查看详情不创建任务。
详情确认绑定打开时的方案 ID/哈希、上下文、模型、环境准入报告和资源回执；
任一变化须关闭并重新核对，历史方案不能确认。繁忙、暂停、待处理消息和执行
条件未满足时禁用确认并说明原因。提交失败保留详情，成功关闭详情并显示任务进度。

资源完成回执必须携带 `conversation-v1`。缺少版本的旧回执默认拒绝处理；维护
恢复仅能对受信任服务追加的、只有 `text` 字段的结果提示追加兼容记录，绑定
原记录 ID/哈希并标记 `legacy_unverified`。恢复不修改原记录，不接受未知版本、
收件/完成队列、动作字段或用户来源，也不生成下载、执行或发布授权。已恢复
记录在回退时须保留兼容读取代码；旧服务仍会拒绝无版本原记录，不可删除审计
历史来回退。该维护能力没有模型、聊天或公共 API 调用入口。

修改草案的 `change-set-proposal-prompt-v2` 允许对冻结的可读文件使用
`kind=append`：绑定原文件 SHA-256，`content` 仅包含新增文本，
`executable=null`，`edits` 使用逐项精确匹配的替换操作。服务器保留其余
原文字节并组装完整 ChangeSet，继续检查批准范围、敏感数据和文件预算。
重试反馈可重复失败文件的完整冻结内容，避免从其他文件复制函数作为锚点。
反馈与仓库源码仍是不可信数据，不能授权任何操作。

对于已耗尽模型次数的格式或锚点错误，受信任的本地维护入口可以提交一次精确
校正；聊天、模型及公共 API 无权调用。`local-proposal-correction-v1` 回执
保存原始校正草案和完整 ChangeSet 的内容寻址制品，绑定失败回执、上下文、
讨论、批准方案及原执行授权，明确来源为 `local_correction`、新增模型调用为零。
失败 Job、模型调用和历史事件不修改。幂等重放返回原回执，内容变化则拒绝。
协调器恢复基线后经正常隔离实施、测试和独立审查继续，不能跳过失败测试。
对话显示校正结果及继续进度，不产生人工作品验收或发布授权。

此事件扩展无需 SQL 迁移。回退前排空或安全停止关联执行并保存数据库和制品；
旧协调器不认识校正回执，会重新拒绝原失败 Job，因此不能让旧服务继续运行
这些未完成任务。不得删除失败记录或修改旧授权来实现回退。

## 会话协议与流程继续请求

`conversation-reasoning-v3` 将证据读取和最终决定分开校验，发布给模型的
schema 同时包含当前可用动作、可引用证据和剩余读取次数。合法只读请求附带
的提前回复、未来引用只作为未采用的展示数据保存，不展示为事实，不派发流程。
混入流程动作、未知字段/工具、敏感数据或未读取的最终引用仍拒绝。最后一次
调用必须根据已有证据结束。纠错原因和工具回执在重启后恢复，原两次调用、
三项读取及任务预算不增加；已排队 v2 作业仍按 v2 解析和原额度运行。

验收请求中的 `prepare_pr=true` 在同一事务记录人工作品验收和
`accepted-publication-v1` 继续请求，直接推进已有规范→文案→预览持久 Job 链，
不再用聊天模型分类确定的下一步。外层事件仍为 `conversation-v1`，领域版本
使用 `continuation_version`。内部请求由协调器记录，不伪装成用户新发言；
对话只展示真实用户消息和来源绑定的进度回执。

已验收且尚无预览的任务有明确下一步：未连接账号时前往设置，连接后可点击
“继续准备 PR 文案和预览”。`POST /publication/continue` 只接受当前验收
`binding_hash`，校验 Origin/CSRF/本地 Token、消息队列、暂停、空闲和幂等键。
失败重试保留请求键，过期绑定拒绝，不能指定任意动作或授予外部写权限。
当前验收、旧失败和模型次数不重写。聊天额度耗尽也不会阻止这个已确认的
确定性步骤，文案自身的原预算仍然生效。

升级只对仍有效验收下、由旧验收按钮自动生成且死于回答校验的准备请求做
一次来源/哈希绑定恢复。后续用户消息、停止或执行变更阻止自动恢复；任意
聊天失败不在恢复范围。新请求与旧失败明确关联。通用作业循环不再重复生成
会话模型作业的最终错误，会话协调器拥有这条消息的完成回执。

预览生成不创建 PR。实际发布、CLA、PR 更新或提交审核继续使用各自精确确认。
预览过期仍可阅读，通过既有“沿用文案更新预览”入口重新核对，不自动延长
确认有效期。该扩展无 SQL 模型变更；回退前排空或停止 v3/继续请求，保留
SQLite 与制品备份。旧服务不能消费新协议，不得删除记录或重置计数来回退。
设计、故障证据和验证边界见 [流程可靠性记录](conversation-workflow-reliability.md)。

## PR 当前状态与历史快照

当前 PR 状态查询必须通过现有 `pr_followup` 持久作业读取 GitHub。明确的
当前状态提问直接排队，不消耗聊天模型次数。即使模型选择 `respond`，协调器
仍检查 `pull_request` 引用：默认必须来自这条查询之后的最新观察；否则拦住
旧回答，派发只读刷新，并等来源绑定的实际结果。不会展示被拦住的旧回答。

用户明确要求上次、历史、缓存状态或不要刷新时，只读取保存的观察。`pull_request`
工具证据包含 `live=false`、`source=saved_observation`、`observed_at` 和
`refresh_action=followup_pr`；读取工具本身不宣称访问了 GitHub。远端不可读
时，本轮查询明确失败，原快照和其观察时间保留，不伪造刷新成功。

合并和关闭状态由可信远端观察及原 PullRequestEvent 链同步。合并优先于单纯
关闭，保留已验证的可选 `merged_at`、`closed_at` 和 `merge_commit_sha`。未知
或不合法时间/提交格式拒绝保存。只从每类最新预览产生待办，已消费预览不回退
到更早未消费版本；已发布、已合并或关闭任务不再出现旧发布/审核确认控件。
终态仍可只读跟进，不提供新的准备发布、提交审核或文案更新模型动作。

该增量不修改 SQL 模型，旧观察缺少可选字段仍可读取；升级追加新观察，保留
原回答、授权和发布链。回退恢复匹配应用版本，并保留所有事件及制品，不得
删除已经观察到的合并状态或改写历史回答。
