## 根源一：局部完成没有转化为用户任务完成

最早对 Oppia 的执行、后来对报告、规划、对话和环境的改造，反复采用
“聚焦回归通过 → 部署健康 → 原任务推进一段”的交付方式。
下一阶段遇到的真实条件往往在下一次用户报障时才验证。

这不是没有测试。现有测试覆盖了大量必要的授权、哈希、恶意输入、恢复和接口边界。
问题是这些证据没有替代真实用户旅程的能力。比如
[多轮对话测试](../tests/test_conversation_workflow_contract.py)在第 309、312、316 行
直接提供正确模型决策和规划结果；[Node 工作流测试](../tests/test_node_workflow.py)
即使选择真实容器，也在第 118–122 行注入实施和审查回复。它们验证服务衔接，
不能证明真实模型在陌生仓库能自己获得正确方案和修改。

UXR-G01、ENV-G01、WB-G03、CX-G02 和 P5-G06 本就保持未通过，文档没有正式宣称
所有门槛已过。但此前面向用户的“已修复”“已完成”经常没有同样清楚地限定范围，
用户因此继续承担下一阶段的平台验收。这是我的交付判断和说明需要改正的地方。

## 根源二：任务闭环分散，外部 Agent 成了流程协调者

系统有持久 Job、批准后的自动实施、Verify、Review 和最多两轮代码修复，
不能说完全没有 Agent 循环。但对话、规划、基线诊断、代码提案、环境恢复和发布后
接续由多套模块处理；同一种失败是否进入诊断和恢复，取决于落在哪个分支。

当前 [contribution_workflow.py](../app/contribution_workflow.py)第 648–703 行仍分开
进行文字设计与结构化修改提案，之后再实施和验证。这个设计本身可以安全运行，
但模型在各段得到的观察、工具、当前源码和完成回执必须一致，不能靠长篇叙述承接。
历史 CodingTurn 有 29,565 和 32,000 字符的助手设计文本；用户实际只需要可执行改动。

当前通用异常分支的 `retryable` 仍主要按四种 Job 名和剩余次数决定
（同文件第 396 行），而基线自动诊断入口只接 `python-workspace-preparation-v3`
（[baseline_feedback.py](../app/baseline_feedback.py)第 104 行）。环境、协议、源码
回归、租约和未知写结果需要各自的恢复契约；单纯有“重试”按钮不能覆盖它们。

维护入口也还在承担实际交付：`record_corrected_proposal(raw=...)`
（[proposal_recovery.py](../app/proposal_recovery.py)第 46 行）允许受信维护者提供
通过校验的新提案。HFlow 事件 241、Excalidraw 事件 122 保存了 `local_correction`，
且 `model_calls_added=0`。这些结果有效，也保留了原授权与失败证据；它们仍属于
外部提供修复内容，不能计为产品自己解决了提案故障。

## 根源三：环境支持范围与被承诺的任务范围不匹配

“改动只有两行”不能证明“仓库的全部检查容易运行”。Salt 的拼写和 Excalidraw
的日志修正，都进入了真实项目完整依赖及检查链；后者消耗了 37 个 Job。

历史环境适配先只支持很窄的锁文件和目录布局，遇到新仓库再逐项补齐。
最近的项目驱动 Node 规格、npm/Yarn/pnpm、Python 动态依赖和独立源码构建是实质进展，
不应仍说当前只支持 package-lock。剩余问题是支持矩阵仍有边界、生命周期还缺
独立验收，复杂服务/浏览器项目也未通用支持。

平台需要在推荐及方案确认前，提供同一份有版本的能力结论，明确区分
“需求小”“源码可读”“静态识别支持”“依赖已准备”“真实检查可运行”。
不能把缺适配说成用户没有确认，也不能在安装成功后就承诺后续全部通过。

## 根源四：模型格式、源码事实和动作回执仍会互相干扰

同类历史问题多次出现：普通提问因 JSON 字段或引用关系失败而整轮终止；
查看已有预览被派发成另一个工作流；模型先说完成，而后台还没产生动作。

Excalidraw 事件 40 明确说“方案已确认，我现在进入实施”，事件 41 随后纠正：
此前没有实施或环境准备，实际是 Yarn 不支持。Salt 事件 171–186 中用户只是
要求查看预览，系统却回复“尚未创建 PR”。HFlow 事件 258–269 的验收后
发布准备同样被对话校验阻断。

这些具体历史路由已有修复：v3 读/最终步骤协议、确定性的验收接续、当前状态刷新
和最新发布后接续都已落地，不能将历史全部报为当前缺陷。需要继续验证的是
新场景下同一类问题是否被通用契约消除，而非只对那句话有效。

底层安全检查必须保留；自然语言说明、结构化提案与实际动作回执应各有职责。
“已执行/已保存/已通过”的事实只能来自已产生并校验的结果。

## 根源五：上下文和预算没有统一，最新一轮仍有可定位缺陷

任务 `17f4852b-7b70-443f-8c6e-4395a8241b9e` 的最后一轮：

| 证据 | 实际内容 |
| --- | --- |
| 事件 298 | 用户：“重新修改方案吧，只改跟本issue的” |
| 事件 301 | conversation checkpoint：输入 45,121 bytes，低于 48,000-byte 压缩目标，`target_met=true` |
| 事件 303 | 实际模型报告 `input_tokens=16478`、`output_tokens=478` |
| Job `289324f5-6b26-4bd2-9ad3-41464030f965` | `failed / conversation_response_budget` |
| 事件 305 | 用户只看到“本轮回答超出预算” |

[conversation_reasoning.py](../app/conversation_reasoning.py)第 231–235 行按字节
压缩并检查输入，调用完成后第 314 行再检查 `input_tokens > 16000`。
本轮输入已经越过该阈值，输出仅 478 token。模型已被调用并记账，流程却在解析
决策前停止。这是系统生成的输入与系统预算规则不一致，不能归因于用户消息太长、
模型账户没额度或模型回答太长。

同一任务还记录了累计输入 2,079,795 token 超过原 2,000,000 上限后，追加到
3,000,000 的历史。目前按现行账本口径为 2,385,891 输入、72,627 输出、31 次
`model_call`；最后一轮不是累计输入 300 万耗尽，而是另一个单次输入阈值。
一些 checkpoint 仍超过其字节目标，例如 241,990 > 160,000。

因此 UXR-T14 按回归规则重开；以前的压缩与恢复实现保留，不能继续将该项整体
标为验证完成。修复需要把模型输入估计、schema/系统提示预留、读取预算、输出
预算和累计账本接起来，并在调用前采取有界措施；不能简单提高阈值或清零历史。

## 根源六：基线问题扩大贡献目标，修复成本由用户承担

双包任务最初由用户明确选择同时修改 OpenAI 与 MistralAI。后者修改前已有三项
类型错误，系统随后反复生成 typing/stub 及 mypy 相关方案，并要求新确认。
其中有不能接受的方案被正确挡住，例如抑制错误或 shadow 源码；但整个任务已
从流式字段修复演变为额外的类型环境处理，用户最后要求只保留本 issue。

当前恢复层还包含针对 `entry_points` 类型错误的专门元数据读取
（[baseline_metadata.py](../app/baseline_metadata.py)第 29 行），规划规则也有
对应特例。这说明修复仍在吸收个案知识，通用的错误归因、最小证据读取与
可执行修复工具尚不足。特例可能必要，但不能持续代替共享能力。

应该分别表达环境故障、原有失败、新引入回归以及未覆盖的缺陷。比较前后结果
需要精确环境与测试证据；是否允许带既有失败交付属于明确的验收决策，
不能擅自放宽当前全部检查通过的要求，也不能把无关修复自动塞进贡献。
若当前规则要求先修基线，应先让用户看到具体范围及成本，或选择真实支持的
独立贡献范围；不应等预算用尽才发现目标无法闭合。

## 为什么外部 Codex 能帮忙，而产品卡住

本次证据支持的差别在职责、工具与反馈。外部 Agent 可以同时读取平台代码、
真实失败产物和上下游调用，修改平台适配器并部署，再通过维护服务恢复任务。
产品里的模型只能使用某阶段发放的有限工具，遇到平台本身的缺陷无法修复平台。
不能把这两种条件下的成果直接拿来比较模型智力；本次没有同条件模型对照。

对于新平台缺陷，停止并由开发者修产品是正常边界。反复的新任务都碰到需要改
平台才能继续的基础问题，说明稳定支持范围与恢复能力尚不足。不能把它们包装成
用户应该会配置、会写特殊提示或会再次点击确认。

现有 `system` / `orchestrator` actor 也不足以证明自动完成：外部维护可以调用同一
服务。最近 PR 生命周期已增加触发来源区分，但尚未覆盖全旅程的自主性统计。
未来应在新记录中明确记录产品自动推进、用户确认及维护触发；旧历史只保留
可证关联，不能反向补造“自动完成”。

## 接下来的修复顺序与通过标准

以下是审查建议，不表示本轮实施或批准了新动作。继续当前 Phase 5；
P5-G06 仍是首个路线图平台门槛。可独立完成同阶段修复，但不进入后续阶段。

1. **先关闭当前可重现缺陷。** 从 UXR-T14 的单次输入预算不一致开始，
   同时保留用户最后的缩范围请求和已消耗用量；修复后通过产品接续，不能由维护
   脚本替模型写新方案来充当该项验收。单纯“重新试试”不算修复。
2. **给每一种失败定义明确去向。** 环境、代码、输出协议、租约、预算和外部
   未知结果分别拥有诊断、剩余额度、恢复动作及停止条件。一个任务协调者负责
   推进和结果回执，各信任域继续分离。确定的后继动作采用类型化持久接续。
3. **固定并公开当前支持范围。** 先选 Python 和 TypeScript 支持矩阵中的
   小任务，检验真实依赖、陌生目录、当前源码加载、缓存、取消与重启；超范围
   提前给出准确的能力缺口，不能误导用户再次批准。
4. **用真实旅程约束局部开发。** 真实模型、容器和原生 UI 连续完成读取、
   方案、精确确认、实施、测试、独立审查、结果确认和只读发布预览。
   默认离线 fakes 继续保护确定性契约；真实验收另存证据。
5. **把维护介入作为产品未通过记录。** 用户表达目标、回答必要问题和确认
   具体动作属于正常使用。外部 Codex 修方案、修业务草案、终端调用维护服务
   或操作数据库均计为维护介入。即使之后成功也不能抹去。

每个支持环境应重复运行新任务，逐轮记录首次成功、格式修复、模型用量、
失败阶段、恢复次数、维护介入及真实测试/审查结果；明确样本和版本。
冻结基准中的新增场景要在运行前确定，不能只回放开发者已知的固定回复。
未通过就继续修当前闭环，不以新增功能或更多测试数量代替。

真实外部发布仍限专用测试账号、非生产仓库和 Draft PR，保留精确一次性确认。
本建议不放宽宿主机执行、凭据、网络、来源链、权限或发布限制。
