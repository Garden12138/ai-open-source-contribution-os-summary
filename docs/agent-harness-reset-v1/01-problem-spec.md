# 01. Problem Specification

## 1. 背景

Runtime v2 已具备持久化任务、模型调用、工具注册、沙箱执行、预算、Checkpoint、工具回执和独立 Review 等基础组件。但真实任务仍可能在 Coding 前消耗大量预算，最终没有源码修改。

本轮目标不是增加更多工具，而是证明 Agent Harness 能否推动真实任务完成闭环。

## 2. Plan11 已观察到的事实

来自分支 `refactor/agent-runtime-v2` 的 Plan11 执行记录：

- 环境准备通过。
- 8 项原生工具入口探针通过。
- 修改前 Baseline 4/4 通过。
- 发生 14 次模型启动，其中 12 次形成有效 Decision，2 次因 5 个工具调用超过单轮上限而整批拒绝。
- 产生 43 个工具结果：`list_paths` 4 次、`read_file` 39 次。
- 没有 `search_code`、`apply_patch` 或 `run_approved_checks` 执行结果。
- 读取结果涉及 6 个源码路径；39 次读取中有 33 次重复使用起始偏移 0。
- 两次超量批次均整批拒绝，实际执行调用数为 0。
- 最终没有源码修改，任务以 `agent_budget_exceeded` 阻塞。

这说明环境准备和读取阶段可以工作，但 Agent 没有从调查推进到修改。

## 3. 核心问题

### P0-A：缺少可验证的任务进度控制

Checkpoint 记录执行状态、源码 Hash、待执行调用和预算，但不能充分表达任务步骤、证据、完成条件和下一步。模型可能在已有读取结果的情况下反复读取。

### P0-B：Provider Tool Calling 与平台批次契约不匹配

平台 Decision 最多允许 4 个调用。Plan11 两次返回 5 个调用，整批拒绝并消耗协议修复额度。不能简单放宽上限，必须检查原始响应、调用身份、顺序、幂等性和写入原子性。

### P0-C：调查、规划、实现、验证之间缺少强制推进契约

模型可以提出工具调用，但系统没有足够强的机制确保任务从调查进入计划、从计划进入实现。

### P1：环境引擎泛化不足

陌生项目 Baseline 和部分 Node 动态安装场景仍有失败。本轮暂不扩大环境引擎支持面，除非其问题直接阻断 Harness 最小验收。

## 4. 本轮目标

1. 引入持久化 Implementation Progress Ledger。
2. 建立任务阶段状态机和合法状态迁移。
3. 对重复工具调用和无进展循环提供确定性检测与恢复。
4. 明确 Provider Adapter、Decision、Tool Scheduler 的职责边界。
5. 保留安全边界，解决模型批次与平台批次的适配问题。
6. 完成 Investigation、Plan、Patch、Verify、Repair、Review。
7. 使用真实模型、真实工具和真实源码完成至少一个端到端任务。

## 5. 非目标

- 不重写 UI 或整个产品。
- 不立即更换 Agent 框架。
- 不全面重构 UPEVE。
- 不扩大 Publisher、自动 PR、自动合并等能力。
- 不通过增加预算掩盖无进展。
- 不用 Mock 结果证明真实模型成功。
- 不把单个 Issue 成功宣称为支持所有开源项目。

## 6. 设计原则

**模型负责推理，平台负责控制。**

平台负责阶段、权限、预算、工具调度、重复调用检测、证据、状态迁移、Verify、Review 和恢复。

**进度必须有证据。** 每个已完成步骤必须引用真实源码读取、搜索、Patch、测试或 Review 回执。模型自然语言声明不能单独构成完成证据。

**安全边界不可绕过。** 写入仍受 `write_paths`、授权、Patch 校验和沙箱限制；Verify 仍绑定当前源码 Hash。

**失败必须可解释。** 阻塞时记录错误码、原因、证据、预算、阶段、下一步和恢复条件。
