## 问题、已证实根因与待验证假设

已证实问题是：工具schema允许的8个read_file大页请求在整批输出准入时安全拒绝，
会话尚有调用次数和Token余额，却没有进入Coding。首次异常为
`app/agent_v2/read_batches.py:159`抛出`agent_read_batch_budget`，
对应第三响应之后的Journal事件2084；该轮原始响应已在事件2082保存。
容量公式、剩余字节与立即终态分支均已有保存证据和对应源码，属于确定事实。

尚待验证的假设是：在不扩大原500000字节上限的情况下，利用OCI证明的实际分页序列化容量，
再为完整ToolResult、进度、失败及相关元数据给出严格上界，能使该真实信封安全通过。
72123字节仅是data预测，不能证明上述完整上界，也不能证明所有后续大页请求均可接受。
另一待评估方向是对真正容量不足提供原额度内的有限纠偏；目前并未实现或验证。

## 补充证据

[容量分析](output-capacity-analysis.json)使用原冻结Context Artifact中的完整文本，
逐文件SHA256核验后仅计算原请求的UTF-8分页与规范JSON长度，没有执行仓库代码。

- 原整批上界：833536字节；当时剩余额度464474。
- 8个实际页的内容合计68338字节。
- 即便保留六倍系数、只按实际文件长度收紧，上界仍475564，超出11090。
- 仅工具data的规范JSON预测合计72123字节；尚未包含完整ToolResult、读取进度、失败和批次元数据。

因此，单纯用文件长度替换max_bytes仍不能证明该信封可执行。
72123也不是完整回执上界，不能直接据此放行；更不能把冻结Context分析冒充当前OCI预检。

## 拟实施的完整范围

1. 先用Plan14保存的第三次真实信封建立离线失败回归，不购买模型重现。
2. 完整验证原8个调用的类型、参数、来源、ID、顺序、授权、源码Hash、沙箱及原预算。
3. 评估在真实OCI全批安全预检中证明每个原始分页的序列化容量，
   同时为完整回执及有界进度/失败元数据提供可验证的保守上界。
   容量证明必须绑定原参数、当前源码、授权、预检版本和原始批次；模型声明不可信。
4. 完整批次所需输出确实可容纳后，才执行最多4-call的持久化子批次。
   不能通过降低系数、删掉预检、隐式缩小max_bytes、删除反馈或放宽500000字节上限来通过。
5. 对真实容量不足继续安全拒绝；若加入可恢复纠偏，使用已有有限额度及准确原因，
   不在已开始的子批次之间请求模型，不为旧Plan14创建新Decision或重置已用预算。
6. 如预检/批次协议字段改变，使用新版本并保持旧Journal、Checkpoint和历史批次可读。
   不编辑任何已冻结Plan/Binding/审批/证据。

预计局限于`app/agent_v2/read_batches.py`、`loop.py`、必要的原生协议声明、
`app/sandbox_worker/agent_tools.py`及相应边界测试；不重构Runtime或扩展UPEVE。
具体算法和差异以验证后的实现为准，不能先把以上设计标成已完成。

## 安全风险与必须保留的控制

| 风险 | 必须保留的控制与反例 |
| --- | --- |
| JSON转义或元数据低估使实际输出超限 | 按真实编码口径证明完整上界，覆盖控制字符、UTF-8边界、外层回执及进度/失败字段；无法证明时拒绝 |
| 模型或伪造工具回执声明较小容量 | 容量证明来自受信OCI接口，绑定原参数/来源/调用ID/顺序/源码Hash/授权；不信任模型给出的长度 |
| 预检后源码、权限或预算变化 | 所有子批次继续检查同一冻结绑定与当前Hash/剩余预算；冲突先停止，保留实际已执行前缀 |
| 为通过预算而静默缩页或丢反馈 | 不改原调用参数，不删原始ID、结果、可见字节范围或next_offset，不扩大原执行/Token/输出上限 |
| 新证明协议破坏旧恢复或造成重复执行 | 新版本明确准入，旧Journal/Checkpoint保持读取兼容；崩溃边界覆盖已完成/未知/未派发状态，不重放已完成调用 |
| 纠偏演变成无限重试或恢复旧付费任务 | 使用原有限额度；Plan14仍为终态，不退还历史预算，不自动创建Plan15或新模型轮次 |

只有上述风险都有对应验证证据，才能把离线修复记为通过；真实不足仍然拒绝。
