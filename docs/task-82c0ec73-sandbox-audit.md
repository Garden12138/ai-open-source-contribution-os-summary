## 失败链与设计问题

1. **把执行准入误认为物理能力。** `app/workbench_view.py` 的 `can_execute`
   依赖已保存方案、状态、空闲与阻断项。没有方案时 false 是正常状态，不能据此
   推断容器无法执行 Python。`execution_context` 将该投影直接交给模型，未拆分
   “Runner 能力”“环境实际准备结果”“方案/授权就绪”。第 6、9、17、21、25 条
   助手事件反复把 builtin + false 说成沙箱不能跑测试，并要求用户本地/CI 执行。
   实际隔离代码读取已成功，但这也不能证明该包的测试环境已经准备好。

2. **环境识别和安装契约只覆盖狭窄布局。** `app/execution_environment.py`
   仅匹配根目录文件，漏掉本任务的
   `python/instrumentation/openinference-instrumentation-openai/pyproject.toml`
   及 `test-requirements.txt`。这个包明确需要 OpenTelemetry、OpenInference、
   OpenAI、respx 等依赖，测试还依赖 pytest 插件；builtin 不代表具备这些工具。
   `app/sandbox_worker/dependencies.py` 的 Python 契约只接收一个带哈希锁文件；
   Node 契约仅接受根目录 package.json + package-lock.json。尚无针对所选子包、
   测试依赖、本地相关包和构建后端的完整环境适配。

3. **缺少修改前真实基线，依赖准备时机过晚。** `schedule_verification` 和
   `DependencyJobWorker` 都要求 Implement 已成功，之后才准备依赖并进入 Verify。
   Implement 中的 `baseline_inventory` 是文件清单，不是修改前测试结果。
   当前不能用相同冻结环境和命令比较修改前后结果，也无法提前证明测试可运行。

4. **工具结果没有约束聊天事实，拒绝诊断不支持恢复。** 第 21、25 条消息都
   声称“已落盘”，而 `plan_id=null`，末尾又追加“尚未保存”。后两次拒绝仅记录
   `planning_output_invalid / value_error / fields=[plan]`；原草稿未保留，
   不能从现有记录确定具体字段或领域约束，不能假称已定位准确拒绝原因。
   第 6、9 条已保存的推迟草稿重新进行 PlanningPlan/plan_content 校验可通过，
   但不等于其执行路径、依赖、命令已经验证。读取后流程也没有可靠完成正式落盘。

5. **成功定义与真实验收不足。** 9 条 Job 成功只表示操作处理结束，其中两次
   明确返回 `plan_status=rejected`。没有任何实际执行证据。聊天关于“已有两项
   预失败”的说法不构成本系统跑过基线的证据；“将先评论 Issue”也不属于获准
   动作，且没有发生。模型调用虽有次数/单次上限，当前仍在大上下文里重复讨论
   相同阻断，缺少针对恢复过程的累计预算与精简上下文策略。

现有 `app/contribution_workflow.py` 已有批准后修改、验证、独立审查及两轮修复的
编排，并非完全没有执行器。问题在于此任务从未到达该入口，且现有环境准备不足以
承诺进入后可运行本项目。只修 can_execute 文案或让草稿保存成功都不算完整解决。

## 应交付的改造

1. **确定性的对话动作与结果。** 用户请求“实现并验证”后，服务生成或修订
   可执行方案，并在对话内提供绑定具体版本和动作的确认卡。由服务展示保存成功、
   待确认、失败原因；模型先说“已保存”不能成为事实。方案错误返回白名单字段级
   原因，在累计调用/时间/token 预算内定向修复；安全失败不保存敏感草稿。
   普通聊天不直接授权执行或外部写入。
2. **工作区环境规格与准备服务。** 按实际修改范围选定子包、工作目录、Python/
   Node 版本、测试入口、本地关联包和精确依赖，生成有版本和哈希的环境规格。
   无现成支持锁文件时，在隔离、无凭据、受限包代理的步骤中解析并冻结依赖，
   产出可复用的锁与环境制品；构建后端与本地包安装也是不可信代码，必须在
   受限容器内完成。验证阶段无网、无模型访问、无凭据；不能把任意 pip/tox
   联网安装塞进 Verify，也不能把给上游增加锁文件当作必须的源码贡献。
3. **提前运行基线。** 在精确批准的 PlanVersion/ExecutionAttempt 内，先准备
   环境、运行约定的修改前测试，再修改并用同一环境和命令做修改后验证。
   新增回归测试还需可追溯的修改前复现。基线失败、环境失败和代码失败分别处理；
   不能通过删测试或改判定来过关。扩展持久阶段/制品须前向迁移、升级与恢复测试。
4. **补齐恢复与闭环。** 保留状态、产物和环境哈希，支持取消、重启和幂等恢复；
   测试失败在批准范围及预算内修复，范围或冻结输入改变则创建新方案并重新确认。
   对话内呈现 diff、真实测试结果及独立审查；运行状态来自 Worker 证据。

正常用户职责是说明目标、回答有必要的范围问题、确认具体执行范围和验收结果。
实现、环境准备、测试与批准范围内的修复由系统完成。尚未适配时明确报告系统缺口，
不能自动转交用户在宿主机安装或执行。
